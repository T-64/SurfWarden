# ADR-0014 计时：对账模型 + 媒体证据 + 片段落库

- 状态：已采纳（2026-10-14）
- 修订：ADR-0003（保留"水位 + 宽限截断"）、ADR-0006

## 背景

v2 的 `step()` 按事件逐个枚举什么时候关段、什么时候开段，条件散落在很多分支里。这带来三个缺陷：

1. 系统一判定为 idle 就停表，看直播和视频（这正是要治理的场景）会严重少计。所有 E2E 都把 idle 阈值调到 3600 秒，绕开了这个问题。
2. 心跳只前移水位，不会让时长落库。一段连续 2 小时的停留，在关段之前的统计里一直是 0，预算和封顶都无法及时触发。
3. 分类在开段时就固定了，后来到达的页面信号（频道）无法改判。

## 决策

1. **对账：** 每个事件只负责更新簿记，然后统一计算"现在应该计时的目标"，和当前段比较；不一致就关段，需要计时就开段。所有分支收敛到一个 `desired()` 加一次比较。
2. **媒体证据：** 系统 idle 时，如果目标标签页 `audible`（来自 chrome tabs），或者 content 报告有视频正在播放且页面可见，就继续计时。锁屏一律停表。
3. **片段落库：** 每次心跳把 `[pieceStart, now − idle阈值]` 落库，同一 `segId` 用 upsert 合并为一行。落库线停在 idle 回溯点之前，因为已经落库的时长无法撤回。实时读数（popup、封顶判断）等于库里的数加上 `liveSeconds()`。
4. **idle 关段回溯：** chrome 在用户无输入满一个阈值后才发出 idle 事件，所以关段时间取 `事件时刻 − 阈值`。
5. 默认 idle 阈值从 60 秒调到 120 秒。读德语课文时一两分钟不碰鼠标是常态；看视频的情况已由第 2 条覆盖。

## 后果

- 看视频的时长计得准了。代价是：页面在后台持续出声、人却离开了，也会被计时，最多一直计到锁屏为止。实际中人离开电脑通常会锁屏，可以接受。
- IndexedDB 写入频率变为约 2 次/分钟，量级可以忽略。
